## SESSION — GEOMETRY: rotate / flip / pad / trim 🏴 (menu A–D)

### Design split (the one decision that shaped it)
Output size determines the home:
- **rotate / flip / pad** — size is a pure function of `(input size, params)` → **`OpSpec`** variants
  (validated by `output_size`, executed via `run_global`, content-addressed by `global_signature`,
  cached, and usable in CLI pipelines).
- **trim** — output size depends on **pixel content** (where the uniform border ends), so it *cannot*
  implement `output_size(Size)→Size`. Like `overlay`/`collage`, it's a **session-direct** engine
  function, not an OpSpec.

### What landed
- domain: `FlipAxis` enum; `OpSpec::{Rotate{degrees,expand}, Flip{axis}, Pad{l,r,t,b,color}}`;
  `rotated_size()` (90° steps swap/keep exactly; other angles → rotated bbox when `expand`);
  `PipelineError::ResultTooLarge` (pad/beautify overflow guard).
- engine `ops.rs`: `rotate` (exact integer permutation for 90° multiples; bilinear inverse-map +
  transparent-corner sampling for arbitrary angles), `flip`, `pad` (crop-style row-run gather onto a
  solid canvas), `content_bounds` (one parallel tile-aware pass → tight non-background bbox) + `trim`
  (crops to that; **content-derived hashes** = tag(rect) ⊕ input hashes, so downstream stays cache-safe;
  returns `None` when the image is entirely background, `input.clone()` when there's no border).
- mcp: `rotate`/`flip`/`pad`/`trim` tools; `parse_axis`; `SessionError::NothingToTrim`; `pad` takes
  `all` for uniform padding.
- cli: **`OPS_HELP` was stale** (missing every `draw_*` + `draw_text` since the annotation/text
  iterations) → rewrote it to list *all* pipeline ops incl. the new geometry ones; strengthened the
  `ops` e2e assertion to guard them. (Bumped the raw string to `r##"…"##` — hex colors like `"#ff0"`
  contain `"#` which closed an `r#"…"#`.)

### Verified
90 tests (domain 13, engine 55, mcp 13+4, cli 1+4), clippy `--all-targets -D warnings` clean.
End-to-end proof over stdio: `rotate 90 → flip → pad(transparent) → trim` **round-trips** back to the
original size (the pad's transparent margin is exactly what trim removes).

### ⚠️ Latent bug found (NOT introduced here, NOT fixed — see BUGS.md)
`compose::overlay`/`collage`/`diff.side_by_side` hash their output tiles by **index only**
(`hash_by_index`), so two different compose results of the same grid size share tile identities. Their
pixels are safe (held by `Arc` in the session map), but a *cached OpSpec run on top of two such outputs*
can collide in the engine cache. Recorded in `BUGS.md`. **trim deliberately avoids this** (content-derived
hashes); `diff`'s difference/heatmap are also safe (content digest via `from_srgb_rgba8`).

### Perf debt (BLAZING follow-ups, logged not fixed)
- `blur`/`beautify` flatten via `to_flat_f32` (a 384 MB alloc at 24 MP) — same pattern resize once had;
  a tile-band streaming blur is the upgrade.
- `redact` `pixelate_region`/`blur_region` read through `pixel()` per sample; `content_bounds` scans
  the whole image. Fine for typical regions/screenshots; tile-direct is the squeeze.
- Correctness first, numbers later — no criterion bench for the new ops yet.

## SESSION — FIX + PERF: compose content-addressing, blur/beautify de-alloc 🏴

Owner: "Фикс бага + перф для blur/beautify".

### Fix — compose is content-addressed now (BUGS.md closed)
The bug: `overlay`/`collage`/`diff.side_by_side` stamped output tiles by index (`hash_by_index`), so two
different compose results of the same grid size shared identities → a cached `OpSpec` layered on top
could collide. **Fix:** each op builds pixels with a private `blend` (index hashes, pixels are all that
matters there), then **re-stamps** the assembled tiles with a content-true signature —
`hash::compose_signature(params, input_tile_hashes…)` (new `craws/cmp` domain) → `global_tile_hash(sig,
i)` via one `stamp` helper. `overlay` folds base+top+(x,y,opacity); `collage` folds all ORIGINAL images +
options (so its index-hashed bg/resize intermediates don't matter); `side_by_side` folds a+b+gap.
- Regression tests: `compose_outputs_are_content_addressed` (identity level) + `compose_outputs_dont_
  poison_the_cache` (end-to-end: two different overlays → exposure each → outputs must differ). Both
  **fail on the old code, pass now.** Gotcha while writing them: the test fixtures (`solid()` via
  `hash_by_index`, `test_image` with a fixed pixel seed) weren't content-addressed, so the first drafts
  false-failed — rebuilt the inputs via `from_srgb_rgba8` with distinct byte digests (mirrors production).

### Perf — blur/beautify no longer flatten the whole image
- **`blur`**: rewritten from `to_flat_f32 → gaussian_blur_flat → from_flat_f32` (3 full-image f32
  buffers + a retile pass, ~1 GB peak at 24 MP) to **tile-row banded/streaming**: per output tile-row,
  horizontal-blur only the ±3σ halo of source rows (streamed via `copy_row_into`) into a small band, then
  vertical-blur that band **straight into the row's tiles**. Peak memory O(width × (256 + 2·radius)) per
  band, independent of image height; zero full-image flat copies. Output is bit-identical (same kernel /
  order / edge-clamp — existing blur tests + the determinism chain still pass). **Measured: 24 MP σ8 cold
  ≈ 495 ms** (new `blur_r8_cold` criterion case).
- **`beautify` shadow**: blurred the silhouette as **1 alpha channel** (new `blur1`) instead of a full
  RGBA buffer (the shadow is premultiplied black, RGB≡0) — 4× less memory + work for the shadow; removed
  the now-dead `over_flat`.
- Still on the list (logged, not done): `redact` region ops + `content_bounds`/`trim` read through
  `pixel()`; `beautify` still flattens source+canvas (fine for screenshot-sized inputs). Criterion for
  the rest of the new ops still owed.

## SESSION — BLAZING pass #3: encode LUT + tile-direct hot paths 🏴

Owner: "Ебашь перф-долг, нужно быть максимально BLAZZZZZING". Attacked the `pixel()`/`powf` hot paths,
measured (criterion `--quick`, 24 MP, bench profile).

### Encode LUT — the headline (every export + future viewport bridge)
`linear_to_srgb8` did a `powf(1/2.4)` per channel — ~106 ms to convert a 24 MP frame to sRGB8. Replaced
with a **65536-entry (16-bit) LUT** baked from the exact transfer at first use: `idx =
clamp(v)·65535; LUT[idx & 0xFFFF]`. Exact for the u8 round-trip (quantization step 1/65535 is ~20× finer
than the tightest sRGB code-point gap near black — the existing `u8_roundtrip_is_exact` test guards it).
**Measured: `tiles_to_srgb8` 24 MP = 106 → 36 ms (~3×).** This is the single most-reused conversion (it
also fronts the planned changed-tiles bridge stream), so it's the highest-leverage win.

### Tile-direct hot paths (kill `pixel()` per sample)
- **`blend`** (overlay/collage/side_by_side): was `top.pixel(tx,ty)` per composited pixel (a tile-lookup
  = two divisions each). Now reads `top` once via `to_flat_f32` and indexes the flat buffer. **`overlay`
  2 MP top on 24 MP = ~18 ms.**
- **`redact`**: `fill`/`pixelate`/`blur` regions were per-pixel `pixel()`. Added `read_region` (tile-direct
  row-run gather, row-parallel) — all three now extract the rect contiguously first; **opaque `fill`
  skips reading the source entirely** (just paints the bar). **`redact` pixelate a 3 MP region on
  24 MP = ~33 ms.**
- Correction to the earlier debt note: `content_bounds`/`trim` were **already** tile-direct (they read
  tile `px` slices, not `pixel()`) — no change needed.

### Left on the list (logged)
- `rotate` arbitrary-angle `sample_bilinear` still uses `pixel()` (it's random-access under rotation;
  a flat-source or last-tile-cache sampler is the fix — deprioritized, rotate-by-angle is rarer).
- `beautify` still flattens source+canvas (fine for screenshot-sized inputs).
- Port-level batch encode, png encode, a fully-streaming resampler — unchanged.
- Criterion for hue_rotate/invert/spotlight still owed.
