## SESSION 3 — M0 SHIPPED 🏴

### What landed
Workspace (`crates/craws-{domain,engine,codecs,cli,mcp}`), edition 2024, rust 1.96, release profile
thin-LTO + cu=1. Built green on the first compile; 43 tests, clippy `--all-targets` 0 warnings.

- **domain**: `Size`/`Rect` (overflow-safe), `Pipeline`/`OpSpec` (serde `op`-tagged JSON — the
  public automation contract), validation folds sizes through the chain.
- **engine**: 256² exact-size tiles of linear premultiplied RGBA f32 behind `Arc`;
  Merkle content addressing (`hash.rs`: src/pw/gl/glt tagged domains) — **pixels hashed at most
  once** (source bytes), all downstream identities derived from params+inputs in microseconds;
  LRU tile cache under a byte budget (default 2 GiB); pointwise ops cached per-tile and computed
  rayon-parallel, global ops (crop/resize) cached per-output-tile under one signature;
  no clamping mid-pipeline — HDR headroom survives to the single clamp point in `linear_to_srgb8`.
- **ops**: exposure (stops), grayscale (Rec.709 in linear), crop (row-run gather straight from
  source tiles), resize (imageops Lanczos3/CatmullRom/bilinear/nearest over premultiplied linear —
  no fringing by construction).
- **codecs**: png/jpeg/webp via `image` (jpeg decode = zune-jpeg internally); jpeg export
  flattens over white; webp lossless.
- **cli**: `craws run pipeline.json --in a.png --out b.webp` with a per-step timing report
  (stderr, `--quiet` to silence), `craws ops` self-documentation, e2e tests driving the real
  binary, `gen_sample` example for 24MP fixtures.

### First numbers (owner's machine, release, 24MP)
CLI end-to-end (PNG → resize+exposure+crop+grayscale → WebP): **556 ms**
(decode 155 / ingest 45 / resize 307 / exposure 5.3 / crop 2.9 / gray 3.2 / encode 18).

Criterion: exposure cold 49 ms → **cached 85 µs**; chain cold 335 ms → **slider-tweak warm
11.8 ms (~85 fps at full 1920px recompute)** — the cache design pays exactly where the product
lives, and that's before mip pyramids and optimistic preview shaders arrive in M2.

⚠️ Found: jpeg **encode** 893 ms (single-threaded image-crate path) vs decode 128 ms —
first entry for a future BUGS/perf list; candidates: jpeg-encoder / mozjpeg behind the same API.

### Notes for future sessions
- Global ops hash at node level (any input tile change recomputes the node). Fine for M0;
  tightening crop to overlapped-tiles-only is a known incremental win.
- Resize goes through a flat buffer (`to_flat_f32` → imageops → retile): simple and correct;
  a streaming tile-band resampler is the BLAZING upgrade path for huge inputs.
- `.memories` grew QUICKSTART / MAP / CONVENTIONS now that there's code to describe.

## SESSION 4 — M2 VIEWPORT-BRIDGE SPIKE 🏴 (jumped ahead of M1 at owner's ask "где веб?")

Owner asked to see the web before M1. M1↔M2 are independent (both are ports over the engine), so
pulled M2 forward. Built the real thing and measured it.

### What landed
- `crates/craws-app` — Tauri 2 shell. Three commands; pixels leave Rust once per frame as ONE raw
  binary payload (`tauri::ipc::Response`, 20-byte LE header + sRGB8) — never JSON. `render` runs
  resize→exposure(→grayscale) on the warm engine and returns the frame.
- `app/` — Vite + React 19 + TS + Tailwind 4 + WebGPU. `renderer.ts` draws a textured quad;
  pan/zoom is a pure GPU transform (uniforms), so navigation never touches the bridge. `ipc.ts` has
  a latest-wins render queue (one in flight, newest params kept) — turns a slider drag into
  back-to-back frames, not a backlog. Overlay shows live engine/convert/bridge/round-trip ms + fps.

### The spike question and the answer
Is Tauri fast enough for a 24MP editor? Measured three paths (full table in STATE.md):
- pan/zoom pure GPU → **165 fps** (display-bound). GPU compositing is free.
- authoritative full-frame slider (engine every tick) → **7.8 fps**, and the cost is **bridge =
  104 ms** to ship a 9.4 MB frame through WebView2 IPC (engine itself only 9 ms). This is the
  bottleneck the plan predicted.
- **optimistic in-shader preview → 165 fps, 0 bridge calls.** Pointwise ops done in the fragment
  shader: sample sRGB8 base → srgb_to_linear → ×exp2(stops) → optional Rec.709 luma → linear_to_srgb.
  Engine renders a neutral base once; slider only writes a uniform; authoritative reconcile on
  pointer-up. Exact for exposure/grayscale (same math as engine), modulo 8-bit base quantization.

**Verdict: the Tauri decision is de-risked with numbers.** The optimistic path (already in the plan)
is 21× the naive one and display-bound. Exit criteria met: pan/zoom ≥60 ✅, slider ≥30 ✅. The
fallback ladder (native wgpu under transparent webview → GPUI) is NOT needed.

### Gotchas caught
- Tauri's `dev` flag = `!custom-protocol` (from tauri's build.rs), **independent of cargo profile**.
  First release build had no `custom-protocol` feature → the exe tried to load the devUrl
  (`localhost:5173`) and showed ERR_CONNECTION_REFUSED. Fix: `[features] default=["custom-protocol"]`
  in craws-app; `tauri dev` builds `--no-default-features` for the live server. (Owner's screenshot
  caught this instantly.)
- `tauri-build` needs `icons/icon.ico` on Windows — generated a placeholder (amber claw marks);
  replace with the real mascot later (owner already sketching a crab mascot — seen in a browser tab).

### Verification
`bun run check` clean, `cargo build --release -p craws-app` clean. Ran the real windowed app; the
startup auto-bench sweeps exposure for 3 s in each mode and prints `BENCH_RESULT …` to stdout.
Two screenshots captured (authoritative 7.8 fps, optimistic 165 fps) — image renders correctly,
slider darkens/brightens live.

## SESSION 5 — M1 MCP SERVER 🏴 "it's alive"

Built `crates/craws-mcp` on the official `rmcp` 2.1 SDK. Researched first: Context7 for rmcp's
current API, and an Explore agent mapped pooprusteek's MCP client precisely (protocol 2024-11-05,
newline-delimited JSON-RPC over stdio, integer id echo, tool results flattened to text — image parts

### Design
- `session.rs` — the engine-facing core with **zero rmcp types**, so it unit-tests directly.
  Image-handle model: open → get `img-N`; every op returns a NEW handle (images immutable, mirroring
  engine tiles); one shared `Engine` means its content-hash cache spans the whole session (batch of
  similar images stays BLAZING). `SessionError` maps caller-fault vs environment-fault.
- `lib.rs` — thin rmcp wrapper. `#[tool_router]`/`#[tool]` for 7 tools; results are compact JSON
  **text** (so the model reads a result's `image_id` and feeds the next call). `get_info` ships
  workflow instructions. Learned: default `#[tool_handler]` rebuilds the router via
  `Self::tool_router()` each call → cached field went unused (clippy) → fixed with
  `#[tool_handler(router = self.tool_router)]` (also avoids per-call rebuild).
- `main.rs` — `serve(stdio())`; **all logging to stderr** (stdout is the protocol channel).

## SESSION 6 — BLAZING debt, pass #1 🏴

Owner: "BLAZING-долг!". Attacked the two worst numbers, measured before/after (criterion, 24MP).

### Resize: own separable resampler (323 → 54 ms, 6×) + architecture win
Replaced `image::imageops::resize` with `crate::resample`: separable two-pass, precomputed
per-output-pixel weights (filter footprint stretched by 1/scale when downsampling to low-pass),
both passes rayon-parallel. The horizontal pass streams source rows straight from the tile grid
(`TiledImage::copy_row_into`) — no 384 MB flat copy of the input; only the out_w×in_h intermediate.
Filters: nearest/bilinear/catmull_rom/lanczos3. **Dropped the `image` dependency from craws-engine
entirely** (it was there only for imageops) — the engine now owns its hot kernel, per the contract.
Real CLI: resize step 307 → 49 ms; full pipeline 556 → 336 ms. Output verified visually (clean
lanczos, no aliasing). +4 resample unit tests (weights sum to 1; solid stays solid; identity
near-lossless; nearest picks source pixels).

### JPEG encode: SIMD encoder (910 → 375 ms, 2.4×)
`image` 0.25 uses its OWN jpeg encoder (zune-jpeg is decode-only) — single-threaded, slow. Swapped
the jpeg *encode* path to the `jpeg-encoder` crate (0.7, pure-Rust SIMD, AVX2 auto-detected); png
and webp stay on `image`. Kept flatten-over-white semantics (tested) and added a 16-bit dimension
guard (JPEG max 65535). Roundtrip + transparency tests still pass.

### Verified
54 tests (was 50, +4 resample), clippy `--all-targets` 0 across the workspace. Benches recorded in
STATE. No commit (owner's rule); tree dirty.

### Notes / remaining debt
- jpeg encode is still single-threaded SIMD; the right place for batch parallelism is the port level
  (encode many files concurrently via rayon), not inside one image — logged in STATE focus.
- The resampler still allocates one intermediate (out_w×in_h); a fully-streaming band resampler is
  only worth it for images that dwarf RAM — deferred.
- export convert does `powf` per channel (~106 ms in ingest+export) — an encode LUT is a clean future win.

## SESSION — BROADEN M1: annotation + composition 🏴 (the killer feature)

Owner's use case: an agent building product docs (Playwright screenshots + Outline) uses craws to
annotate — arrows, circles, boxes with color/stroke-width/corner-radius/fill/opacity — plus overlay
screenshots and make smart collages. Text deferred to the next iteration (agreed).

### Design decision: SDF rasterizer in linear light, NOT tiny-skia
The engine is linear-premultiplied f32; tiny-skia draws in sRGB8 u8, which would break the invariant
and clamp HDR. So the annotation rasterizer is our own: analytic **signed-distance fields** (rounded
rect, ellipse, segment) → 1px anti-aliased coverage → composite paint (converted to linear premul) in
**linear light**. Only tiles overlapping the shape bbox recompute; the rest are Arc-cloned. The same
coverage→composite path will drive text glyph masks next iteration (so this isn't a throwaway).

### Two op classes (a small step toward the future node graph)
- **Annotation = single-input** → new `OpSpec` variants (`draw_rect/ellipse/line/arrow`), run through
  the normal cached pipeline. Domain holds `Rgba8` (straight sRGB); engine converts at draw time.
- **Composition = multi-input** (overlay, collage) → can't be a single-input `Pipeline`, so they're
  `craws-engine::compose` functions the MCP `Session` calls directly with several handles.

### What landed
- domain: `color.rs` (`Rgba8`), 4 draw OpSpec variants + validation (finite geometry, non-negative
  dims, "nothing to draw" when no fill/stroke).
- engine `draw.rs`: `Paint`, SDF primitives, `rect/ellipse/line/arrow`; arrow = shaft + two head
  segments unioned by min-distance. `compose.rs`: `overlay` (paste at x,y + opacity, src-over) +
  `collage` (justified-rows layout by aspect — Flickr/Google-Photos style — resize each cell with our
  Lanczos3, overlay onto a solid background).
- mcp: 6 new tools + `parse_color` (`#RGB`/`#RRGGBB`/`#RRGGBBAA`/names). Session `overlay`/`collage`.
- Tests: 71 total (was 54). New: draw SDF coverage (interior/edge/transparency-blend), compose
  (overlay offset/opacity/crop, collage width/coverage/layout), color parsing, and a stdio test that
  annotates + collages over the real wire.

### Verified visually (the real proof)
`mcp_annotate_demo.py` built two PIL screenshot mockups (login form, dashboard) and drove the release
binary over stdio: rounded red box on the Sign-in button, orange circle on the help icon, blue arrow
(with head) at the email field, translucent green highlight on the password row → exported PNG looks
exactly like a hand-made how-to. Then a 3-shot justified collage on a navy bg, 1400px wide. Both
opened and eyeballed — clean AA, correct colors, correct alpha blend, aspect-preserving cells.

### Notes
- Colors default alpha to 255; collage bg defaults to white; stroke/thickness default 3, head 18.
- Draw ops hash at node level (whole-image signature) even though only the bbox changes — fine now;
  a bbox-scoped hash is a future micro-opt.
- No commit (owner's rule).
